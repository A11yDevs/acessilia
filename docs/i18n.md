# Internationalization (i18n)

You can also read this document in **Brazilian Portuguese**: [português brasileiro](i18n.pt-br.md)

Acessilia is fully internationalized in the locales `en_US` (default) and `pt_BR`. This document explains what the software localizes, where the locale strings live, and gives step-by-step recipes (with shell examples) for adding new strings, internationalizing an existing python file, and adding a new locale.

## What Internationalization Features Acessilia Supports

The project uses **Babel** (`babel` in `../pyproject.toml`) as the base of its localization system. User-facing strings are variablized through per-locale strings files, and the runtime-selected locale decides which strings file is used for variable substitution — adding a new supported locale requires only one new strings file (minimal code changes). Runtime error messages shown to users in the REST API and the Telegram bot during upload validation (such as "unsupported format", "file too large"), Telegram bot command responses, email subjects and bodies, web-panel UI labels, and all server-side log lines are resolved from catalogs at `backend/locales/<locale>/LC_MESSAGES/messages.po`.

Concretely, the runtime supports:

- **Server-side locale negotiation.** At startup, the active locale is negotiated from the `.env` file's `LOCALE` setting, then if that isn't set, the `LOCALE` (or `LANGUAGE`, `LC_ALL`, `LANG`) environment variables against the supported locales (`en_US`, `pt_BR`), falling back to the default `en_US`. See [backend/i18n.py](../backend/i18n.py) (`_locale_from_env`).
- **Per-user locale.** The Telegram bot detects each sender's language code (Telegram `from_user.language_code`) in [frontend/telegram/middlewares/locale_middleware.py](../frontend/telegram/middlewares/locale_middleware.py) and overrides the lookup locale for that task only, through `set_request_locale()`/`locale_for_user()` in [backend/i18n.py](../backend/i18n.py). So log output stays in the server locale while every reply to a user is in the user's own locale when it is one of the offered locales; otherwise the user sees the server-side locale as well. A bare language code (e.g. `pt`) leniently resolves to the offered regional locale (`pt_BR`).
- **Canonical message ids.** Code looks up strings through `t()` (and `n()` for plurals) in [backend/i18n.py](../backend/i18n.py) using canonical English message ids defined as `MSG_*`/`LOG_*`/`EXE_*` constants (e.g., in [backend/tools/validators.py](../backend/tools/validators.py), [backend/log_messages.py](../backend/log_messages.py), and [frontend/telegram/messages.py](../frontend/telegram/messages.py)). If a translation is missing for the active locale, Babel falls back to the English msgid unchanged.
- **Locale-aware Telegram slash commands.** Portuguese slash commands (`/ativar`, `/desativar`, `/ajuda`, `/formatos`, ...) keep working regardless of locale, and each has a US English alias (`/activate`, `/deactivate`, `/help`, `/formats`, ...) registered side by side in [frontend/telegram/handlers/start.py](../frontend/telegram/handlers/start.py). Command listings and all command responses render in the user's locale via the same catalogs.
- **Offered-locale list.** `I18N_LOCALES_ACTIVE` in `.env` (comma-separated) controls which locales the software advertises and offers to remote users; the bot only ever returns locales from that list.
- **Local log localization.** All server-side logging resolves its messages through the same catalogs in *the server's* locale (the `LOCALE` setting), independent of any per-user override.
- **Email localization.** Confirmation and result e-mails (subjects and bodies) are localized in the recipient's locale when known, otherwise the server's locale, via the `EMAIL_*` canonical msgids registered in [backend/log_messages.py](../backend/log_messages.py).
- **Web panel localization.** The web panel renders its UI labels in the active locale, see [frontend/web/messages.py](../frontend/web/messages.py) and [frontend/web/app.py](../frontend/web/app.py).

In every file excerpt in this document, lines starting with `+` mark added or changed content; surrounding unmarked lines are unchanged context, and lines starting with `-` are removed content.

## Where are the I18N Files and Directories

- **Canonical msgid constants** (English strings that act as the lookup ids) live next to the code that emits them, grouped by concern:
  - [backend/log_messages.py](../backend/log_messages.py) — server-side log lines and email subjects/bodies (`LOG_*`, `EMAIL_*`, `API_*`).
  - [backend/stage_messages.py](../backend/stage_messages.py) — user-facing pipeline stage/status strings (`MSG_*`).
  - [backend/core/execution/messages.py](../backend/core/execution/messages.py) — executor error and status strings (`EXE_*`).
  - [backend/tools/validators.py](../backend/tools/validators.py), [backend/tools/prompt_tools.py](../backend/tools/prompt_tools.py), [backend/export/pandoc_exporter.py](../backend/export/pandoc_exporter.py), [backend/core/manifest/docling_extractor.py](../backend/core/manifest/docling_extractor.py) — per-module `MSG_*`/error strings.
  - [frontend/telegram/messages.py](../frontend/telegram/messages.py) — every Telegram bot string, including command texts.
  - [frontend/web/messages.py](../frontend/web/messages.py) — web panel UI strings.
- **Locale strings files (compiled catalogs)** live in [backend/locales/](../backend/locales/), one directory per locale:
  - `backend/locales/en_US/LC_MESSAGES/messages.po` — human-readable English source catalog (msgids map to themselves, the identity catalog).
  - `backend/locales/en_US/LC_MESSAGES/messages.mo` — compiled binary catalog actually loaded at runtime.
  - `backend/locales/pt_BR/LC_MESSAGES/messages.po` and `messages.mo` — same pair for Brazilian Portuguese.
- **Catalog generator:** [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) is the single source of truth for catalog content. It imports every msgid constant, validates complete coverage, then rewrites both locales' `.po` files and compiles the `.mo` binaries. Do not hand-edit the `.po`/`.mo` files — they are regenerated artifacts.
- **Configuration:** the bottom of [.env.example](../.env.example) (and of the active `.env`) holds the "I18N" section.
- **Tests:** [tests/test_i18n.py](../tests/test_i18n.py) covers catalog coverage, English fallback on missing entries, and format-placeholder preservation.

## How to Add a New Internationalized String to the Code

Worked example: add an `MSG_DOWNLOAD_READY` canonical message shown to users when their document finishes processing. The locale catalogs stay complete (the generator rejects partial coverage), so follow all four steps below.

1. Define the message as a canonical English `MSG_*` constant in the module that emits it (validators and Telegram handlers each own their own constants). Open the file in your editor of choice — the examples use `emacs`, but you can substitute any text editor:

   ```bash
   emacs backend/tools/validators.py
   ```

   Add the constant next to the existing `MSG_*` constants near line 13 (a couple of lines above that point):

   ```python
   #: Canonical English msgid template for the oversized-file error; {limit} is substituted by callers after lookup.
   MSG_FILE_TOO_LARGE: str = "File too large. Limit: {limit} MB."
   +#: Canonical English msgid shown when a finished job's exports are ready to download.
   +MSG_DOWNLOAD_READY: str = "Download ready."
   ```

2. Use the constant where needed via `backend.i18n.t(...)`; format placeholders like `{limit}` stay on the strings themselves so every locale can localize them independently (illustrative placement — put the call in whichever function surfaces your message):

   ```bash
   emacs backend/tools/validators.py
   ```

   Next to the existing localized calls:

   ```python
           return False, t(MSG_UNSUPPORTED_FORMAT)
       else:
   -       return False, t(MSG_FILE_TOO_LARGE).format(limit=settings.max_file_size_mb)
   +   # Example style: look up once through t(); placeholders are resolved per locale and substituted by this caller.
   +   return True, t(MSG_DOWNLOAD_READY)   # English "Download ready." in en_US; pt_BR from the catalog at runtime.
   ```

3. Register the constant in [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py):
   - add it to the `MESSAGES` tuple (importing it first), and
   - provide a non-blank translation for every non-default locale in `TRANSLATIONS` — the generator refuses to write catalogs until every id is fully covered, so forgetting one fails loudly with an error listing what is missing.

   ```bash
   emacs scripts/gen_locale_catalogs.py
   ```

   First extend the import for `backend.tools.validators` at line 282:

   ```python
   -from backend.tools.validators import MSG_FILE_TOO_LARGE, MSG_UNSUPPORTED_FORMAT
   +from backend.tools.validators import (MSG_DOWNLOAD_READY, MSG_FILE_TOO_LARGE, MSG_UNSUPPORTED_FORMAT)
   ```

   then add the id to `MESSAGES`:

   ```python
   MESSAGES: tuple[str, ...] = (
    "Processing your document…",
    "Job complete: your file is ready for download",
    MSG_UNSUPPORTED_FORMAT,
    MSG_FILE_TOO_LARGE,
   +   MSG_DOWNLOAD_READY,
    # Pipeline processing-stage labels surfaced to end users as live progress
    # (backend/service.py, backend/agents/*, backend/api/worker.py).
   ```

   and give it a translation in the `pt_BR` table of `TRANSLATIONS`:

   ```python
   "pt_BR": {
      ...existing entries...
       MSG_FILE_TOO_LARGE: "Arquivo muito grande. Limite: {limit} MB.",
   +   # The generator requires at least one non-blank value per id in every non-default locale.
   +   MSG_DOWNLOAD_READY: "Download pronto.",
   ```

4. Regenerate all locale catalogs:

   ```bash
   poetry run python scripts/gen_locale_catalogs.py
   # Expected output naming the refreshed artifacts, e.g., en_US and pt_BR LC_MESSAGES paths under backend/locales/.../ with the compiled .messages.mo files that get printed in alphabetical order per language.
   ```

Verification is covered by [tests/test_i18n.py](../tests/test_i18n.py):

```bash
poetry run pytest   # or narrowly, poetry run pytest tests/test_i18n.py; green results confirm coverage, English fallback on missing entries, and preservation of format placeholders.
LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Download ready.'))"
# Expected: Download pronto.  → proof the new msgid resolves through that locale's compiled catalog.
```

## How to Internationalize an Already Written Code File

Use this recipe to turn a file that still carries hardcoded literals (Portuguese or English) into the catalog-driven pattern above.

1. **Find the hardcoded literals.** Grep the file for user-facing string literals in its source language. Portuguese literals tend to contain accented characters, which makes them easy to spot:

   ```bash
   grep -n "Exportando\|falha\|Erro\|Arquivo" backend/example_module.py   # expected: line numbers plus the hardcoded lines that must move into a catalog
   grep -n 'logger\.\(info\|debug\|warning\|error\|critical\)(' backend/example_module.py   # expected: every log call site to check for hardcoded text
   ```

   Note every literal and where it is emitted (log line, `raise`, HTTP/Telegram response, or email body).

2. **Choose the owning constants module** so ids stay next to their concern:
   - server-side log lines and emails → append `LOG_*`/`EMAIL_*` ids to [backend/log_messages.py](../backend/log_messages.py);
   - pipeline stage/status text users see → [backend/stage_messages.py](../backend/stage_messages.py);
   - executor errors → [backend/core/execution/messages.py](../backend/core/execution/messages.py);
   - Telegram bot text → [frontend/telegram/messages.py](../frontend/telegram/messages.py);
   - web panel UI text → [frontend/web/messages.py](../frontend/web/messages.py);
   - module-local errors or messages → define the `MSG_*` constants at the top of the file itself (the pattern in [backend/tools/validators.py](../backend/tools/validators.py)).

   Each new constant is the **canonical English text** (with `{placeholder}` markers for variables) plus a `#:` comment describing it, e.g.:

   ```python
   +#: Log message emitted once per export; {path} is the destination path substituted by the caller after lookup.
   +LOG_EXPORT_START: str = "Exporting {format} to {path}"
   ```

3. **Rewrite every call site** to look the id up at emission time, keeping placeholder substitution on the caller side:

   ```python
   -    logger.info(f"Exportando {fmt} para {dest}")
   +    logger.info(t(LOG_EXPORT_START).format(format=fmt, path=dest))
   ```

   and translate any non-English docstrings/comments in the touched file to US English with typed parameters per the project's code-quality rules.

4. **Register the constants in the generator.** Add the import and the ids to `MESSAGES` in [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py), and add a non-blank Portuguese translation for each to the `TRANSLATIONS["pt_BR"]` table (preserve the original Portuguese wording exactly when it came from hardcoded strings, so user-visible text does not change).

5. **Regenerate and verify:**

   ```bash
   poetry run python scripts/gen_locale_catalogs.py   # rewrites both .po sources and compiles both .mo binaries
   poetry run pytest tests/test_i18n.py               # green means coverage, fallback, and placeholders all check out
   LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Exporting {format} to {path}').format(format='TXT', path='var/out.txt'))"
   # Expected: pt_BR wording of the moved message with the variables substituted — proof the id resolves through the catalog.
   ```

## How to Add a New Locale and Activate It

Adding a locale (e.g. `es_ES`) is intentionally small: one translation table and configuration, no changes to business logic.

1. **Activate the locale in the configuration files** (`.env` and `.env.example`, in the bottom I18N section):

   ```bash
   emacs .env
   ```

   ```
   # I18N Configuration
   #LOCALE=pt_BR
   -I18N_LOCALES_ACTIVE=en_US,pt_BR
   +I18N_LOCALES_ACTIVE=en_US,pt_BR,es_ES
   ```

   `I18N_LOCALES_ACTIVE` controls which locales are offered to remote users; `LOCALE` (when set) selects the server-side locale used for logging and default output.

2. **Declare the locale to the runtime.** Add the identifier to `SUPPORTED_LOCALES` in [backend/i18n.py](../backend/i18n.py) (line ~20) and to `SUPPORTED_LOCALES` in [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) (line ~409), so negotiation, the bot's offered-locale list, and catalog generation all include it:

   ```python
   -SUPPORTED_LOCALES: tuple[str, ...] = ("en_US", "pt_BR")
   +SUPPORTED_LOCALES: tuple[str, ...] = ("en_US", "pt_BR", "es_ES")
   ```

3. **Provide the translation table.** In [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py), add an `es_ES` mapping to `TRANSLATIONS` with a non-blank entry for **every** id in `MESSAGES` — the generator validates completeness and refuses to write catalogs while any id is missing, so the first run fails loudly until coverage is complete. Keep placeholder names in `{variable}` form identical to the English strings:

   ```python
   "es_ES": {
       MSG_FILE_TOO_LARGE: "Archivo demasiado grande. Límite: {limit} MB.",
       MSG_DOWNLOAD_READY: "Descarga lista.",
       # ...one non-blank entry per id in MESSAGES...
   }
   ```

4. **Generate the new locale's strings files.** The generator now writes `backend/locales/es_ES/LC_MESSAGES/messages.po` and compiles `messages.mo` beside it, exactly like the existing locales:

   ```bash
   poetry run python scripts/gen_locale_catalogs.py
   # Expected output now lists the new es_ES LC_MESSAGES path in addition to en_US and pt_BR.
   ls backend/locales/es_ES/LC_MESSAGES/   # expected: messages.po and messages.mo
   ```

5. **Verify at runtime and test:**

   ```bash
   LOCALE=es_ES poetry run python -c "from backend.i18n import t, active_locale; print(active_locale(), '|', t('Download ready.'))"
   # Expected: es_ES | Descarga lista.  → proof the new locale catalog loads and resolves.
   poetry run pytest                          # full suite still green, including tests/test_i18n.py coverage checks
   ```

   For anything user-visible in the new locale, check glyph coverage on recent Linux, macOS, and Windows versions (prefer widely supported symbols over exotic emoji).

## Viewing and Editing Existing Translations

- **Viewing.** Human-readable translations live in the compiled-pair source files: [backend/locales/en_US/LC_MESSAGES/messages.po](../backend/locales/en_US/LC_MESSAGES/messages.po) for English and [backend/locales/pt_BR/LC_MESSAGES/messages.po](../backend/locales/pt_BR/LC_MESSAGES/messages.po) for Brazilian Portuguese. Open either file to inspect msgids, localized texts, format placeholders, and plural rules.

  ```bash
  cat backend/locales/pt_BR/LC_MESSAGES/messages.po    # shows the pt-BR source header and the leading msgid/msgstr pairs.
  grep -n -A1 'Processing your document' backend/locales/pt_BR/LC_MESSAGES/messages.po
  # e.g.: msgid "Processing your document…"
  #     msgstr "Processando seu documento…"   (line numbers shift as new messages are added.)
  ```

  The runtime actually loads the compiled binary `messages.mo` files beside each `.po`; the default English identity catalog maps every msgid to itself. Verify what a locale really serves at runtime:

  ```bash
  LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Processing your document…'))"   # expected: Processando seu documento…
  LOCALE=en_US  poetry run python -c "from backend.i18n import t; print(t('Processing your document…'))"   # expected: Processing your document…
  ```

  For a full-stack check, start the stack under the desired locale and exercise the API or bot:

  ```bash
  cp .env.example .env 2>/dev/null || true    # only if you do not already have a .env (ignore if you do).
  LOCALE=pt_BR poetry run python -m frontend.run   # then, e.g., send the bot an oversized file and expect the pt-BR "Arquivo muito grande." text, or call /health for a localized status description.
  ```

- **Editing.**
  1. Edit the affected locale's entries in the `TRANSLATIONS` section of [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) (the `.po` files are regenerated artifacts — do not hand-edit them or your changes will be overwritten on the next run).
  2. Re-run the generator to rewrite the locale's `.po` and compiled `.mo`:

     ```bash
     poetry run python scripts/gen_locale_catalogs.py
     ```
  3. Keep placeholder names in `{variable}` form identical across all locales so caller-side substitution keeps working, and mind glyph coverage on recent Linux, macOS, and Windows versions for anything user-visible (e.g., prefer widely supported symbols over exotic emoji where possible).
  4. Run `poetry run pytest` to confirm the i18n suite still passes.
