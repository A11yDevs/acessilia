# Internacionalização (i18n)

Você também pode ler este documento em **inglês**: [English](i18n.md)

Acessilia é totalmente internacionalizada nos locales `en_US` (padrão) e `pt_BR`. Este documento explica o que o software localiza, onde os arquivos de strings por locale ficam, e fornece receitas passo a passo (com exemplos de shell) para adicionar novas strings, internacionalizar um arquivo python já escrito, e adicionar um novo locale.

## Quais Funcionalidades de Internacionalização o Acessilia Suporta

O projeto usa **Babel** (`babel` no [../pyproject.toml](../pyproject.toml)) como base do sistema de localização. Os textos visíveis ao usuário são variabilizados por meio de arquivos de strings por locale, e o locale escolhido em runtime decide qual arquivo de strings é usado para a substituição de variáveis — adicionar um novo locale suportado exige apenas um novo arquivo de strings (mudanças mínimas de código). As mensagens de erro exibidas aos usuários na API REST e no bot do Telegram durante a validação de upload (formato não suportado, arquivo grande demais), as respostas aos comandos do bot do Telegram, os assuntos e corpos de e-mails, os rótulos da interface do painel web e todas as linhas de log do servidor são resolvidas dos catalogs em `backend/locales/<locale>/LC_MESSAGES/messages.po`.

Concretamente, o runtime suporta:

- **Negociação de locale no servidor.** Na inicialização, o locale ativo é negociado a partir da variável `LOCALE` do arquivo `.env`, então se ela não estiver definida, de variáveis de ambiente `LOCALE` (ou `LANGUAGE`, `LC_ALL`, `LANG`) contra os locales suportados (`en_US`, `pt_BR`), caindo no padrão `en_US`. Veja [backend/i18n.py](../backend/i18n.py) (`_locale_from_env`).
- **Locale por usuário remoto.** O bot do Telegram detecta o código de idioma de cada remetente (`from_user.language_code` do Telegram) em [frontend/telegram/middlewares/locale_middleware.py](../frontend/telegram/middlewares/locale_middleware.py) e sobrescreve o locale de consulta apenas para aquela tarefa, por meio de `set_request_locale()`/`locale_for_user()` em [backend/i18n.py](../backend/i18n.py). Assim, o log permanece no locale do servidor enquanto toda resposta a um usuário sai no próprio locale do usuário, quando ele for um dos locales oferecidos; caso contrário, o usuário vê também o locale do servidor. Um código de idioma bare (p. ex. `pt`) se resolve com tolerância ao locale regional oferecido (`pt_BR`).
- **IDs de mensagens canônicos.** O código busca as strings por meio de `t()` (e `n()` para plurais) em [backend/i18n.py](../backend/i18n.py), usando ids de mensagens canônicos em inglês definidos como constantes `MSG_*`/`LOG_*`/`EXE_*` (p. ex., em [backend/tools/validators.py](../backend/tools/validators.py), [backend/log_messages.py](../backend/log_messages.py) e [frontend/telegram/messages.py](../frontend/telegram/messages.py)). Se uma tradução estiver ausente para o locale ativo, o Babel recorre ao msgid original em inglês sem modificação.
- **Comandos de barra (slash) do Telegram conscientes do locale.** Os comandos portugueses (`/ativar`, `/desativar`, `/ajuda`, `/formatos`, ...) continuam funcionando independentemente do locale, e cada um possui um alias em inglês americano (`/activate`, `/deactivate`, `/help`, `/formats`, ...) registrado lado a lado em [frontend/telegram/handlers/start.py](../frontend/telegram/handlers/start.py). As listagens de comandos e todas as respostas de comandos são renderizadas no locale do usuário pelos mesmos catalogs.
- **Lista de locales oferecidos.** `I18N_LOCALES_ACTIVE` no `.env` (separado por vírgulas) controla quais locales o software anuncia e oferece aos usuários remotos; o bot só retorna locales dessa lista.
- **Log local localizado.** Todo o log do servidor resolve suas mensagens pelos mesmos catalogs no *locale do servidor* (a configuração `LOCALE`), independentemente de qualquer sobrescrita por usuário.
- **E-mails localizados.** Os e-mails de confirmação e de resultado (assunto e corpo) são localizados no locale do destinatário, quando conhecido, senão no locale do servidor, via os msgids canônicos `EMAIL_*` registrados em [backend/log_messages.py](../backend/log_messages.py).
- **Painel web localizado.** O painel web renderiza seus rótulos de interface no locale ativo; veja [frontend/web/messages.py](../frontend/web/messages.py) e [frontend/web/app.py](../frontend/web/app.py).

Em todos os trechos de arquivo deste documento, linhas iniciadas por `+` marcam conteúdo adicionado ou modificado; linhas circundantes sem marca são contexto inalterado, e linhas iniciadas por `-` são conteúdo removido.

## Onde Ficam os Arquivos e Diretórios de I18N

- **Constantes de msgid canônicos** (strings em inglês que funcionam como ids de consulta) ficam ao lado do código que as emite, agrupadas por preocupação:
  - [backend/log_messages.py](../backend/log_messages.py) — linhas de log do servidor e assuntos/corpos de e-mail (`LOG_*`, `EMAIL_*`, `API_*`).
  - [backend/stage_messages.py](../backend/stage_messages.py) — strings de estágio/status do pipeline visíveis ao usuário (`MSG_*`).
  - [backend/core/execution/messages.py](../backend/core/execution/messages.py) — strings de erro e status do executor (`EXE_*`).
  - [backend/tools/validators.py](../backend/tools/validators.py), [backend/tools/prompt_tools.py](../backend/tools/prompt_tools.py), [backend/export/pandoc_exporter.py](../backend/export/pandoc_exporter.py), [backend/core/manifest/docling_extractor.py](../backend/core/manifest/docling_extractor.py) — strings `MSG_*`/de erro por módulo.
  - [frontend/telegram/messages.py](../frontend/telegram/messages.py) — toda string do bot do Telegram, incluindo textos de comandos.
  - [frontend/web/messages.py](../frontend/web/messages.py) — strings de interface do painel web.
- **Arquivos de strings por locale (catalogs compilados)** ficam em [backend/locales/](../backend/locales/), um diretório por locale:
  - `backend/locales/en_US/LC_MESSAGES/messages.po` — catálogo-fonte inglês legível por humanos (msgids mapeiam a si mesmos, o catálogo identidade).
  - `backend/locales/en_US/LC_MESSAGES/messages.mo` — catálogo binário compilado que é carregado de fato em runtime.
  - `backend/locales/pt_BR/LC_MESSAGES/messages.po` e `messages.mo` — o mesmo par para o português do Brasil.
- **Gerador de catalogs:** [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) é a única fonte de verdade para o conteúdo dos catalogs. Ele importa toda constante de msgid, valida a cobertura completa e reescreve os arquivos `.po` dos dois locales, compilando os binários `.mo`. Não edite os arquivos `.po`/`.mo` à mão — eles são artefatos regenerados.
- **Configuração:** o rodapé do [.env.example](../.env.example) (e do `.env` ativo) contém a seção de "I18N".
- **Testes:** [tests/test_i18n.py](../tests/test_i18n.py) cobre a cobertura dos catalogs, o fallback para inglês quando entradas faltam e a preservação dos placeholders de formatação.

## Como Adicionar uma Nova String Internacionalizada ao Código

Exemplo prático: acrescente a mensagem canônica `MSG_DOWNLOAD_READY`, exibida aos usuários quando o processamento do documento termina. Os catalogs de locales permanecem completos (o gerador rejeita cobertura parcial), então siga os quatro passos abaixo.

1. Defina a mensagem como constante `MSG_*` canônica em inglês no módulo que a emite (validators e handlers do Telegram possuem cada um suas próprias constantes). Abra o arquivo no editor de sua escolha — os exemplos usam `emacs`, mas qualquer editor de texto serve:

   ```bash
   emacs backend/tools/validators.py
   ```

   Acrescente a constante junto às constantes `MSG_*` existentes, por perto da linha 13 (algumas linhas acima desse ponto):

   ```python
   #: Canonical English msgid template for the oversized-file error; {limit} is substituted by callers after lookup.
   MSG_FILE_TOO_LARGE: str = "File too large. Limit: {limit} MB."
   +#: Canonical English msgid shown when a finished job's exports are ready to download.
   +MSG_DOWNLOAD_READY: str = "Download ready."
   ```

2. Use a constante onde for necessário via `backend.i18n.t(...)`; placeholders de formatação como `{limit}` ficam nas próprias strings, para que cada locale possa localizá-los independentemente (posicionamento ilustrativo — coloque a chamada na função que exibir sua mensagem):

   ```bash
   emacs backend/tools/validators.py
   ```

   Ao lado das chamadas já localizadas:

   ```python
           return False, t(MSG_UNSUPPORTED_FORMAT)
       else:
   -       return False, t(MSG_FILE_TOO_LARGE).format(limit=settings.max_file_size_mb)
   +   # Estilo de exemplo: busque uma única vez via t(); placeholders são resolvidos por locale e substituídos por este chamador.
   +   return True, t(MSG_DOWNLOAD_READY)   # "Download ready." em inglês para en_US; pt_BR vem do catalog em runtime.
   ```

3. Registre a constante em [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py):
   - adicione-a à tupla `MESSAGES` (importando-a antes), e
   - forneça uma tradução não vazia para todos os locales não padrão no dicionário `TRANSLATIONS` — o gerador se recusa a escrever os catalogs até que todo id esteja totalmente coberto; esquecer um deles falha com clareza, listando em erro o ponto ausente.

   ```bash
   emacs scripts/gen_locale_catalogs.py
   ```

    Primeiro estenda o import de `backend.tools.validators` na linha 282:

    ```python
    -from backend.tools.validators import MSG_FILE_TOO_LARGE, MSG_UNSUPPORTED_FORMAT
    +from backend.tools.validators import (MSG_DOWNLOAD_READY, MSG_FILE_TOO_LARGE, MSG_UNSUPPORTED_FORMAT)
    ```

    depois acrescente o id à `MESSAGES`:

    ```python
    MESSAGES: tuple[str, ...] = (
        "Processing your document…",
        "Job complete: your file is ready for download",
        MSG_UNSUPPORTED_FORMAT,
        MSG_FILE_TOO_LARGE,
    +   MSG_DOWNLOAD_READY,
        # Pipeline processing-stage labels surfaced to end users as live progress
        # (backend/service.py, backend/agents/*, backend/api/worker.py).
    ```

    e dê uma tradução na tabela `pt_BR` de `TRANSLATIONS`:

   ```python
   "pt_BR": {
      ...entradas existentes...
       MSG_FILE_TOO_LARGE: "Arquivo muito grande. Limite: {limit} MB.",
   +   # O gerador exige pelo menos um valor não vazio por id em todo locale não padrão.
   +   MSG_DOWNLOAD_READY: "Download pronto.",
   ```

4. Regenere todos os catalogs de locales:

   ```bash
   poetry run python scripts/gen_locale_catalogs.py
   # Saída esperada anunciando os artefatos atualizados, p. ex., paths LC_MESSAGES para en_US e pt_BR sob backend/locales/.../ com os arquivos .messages.mo compilados impressos em ordem alfabética por language.
   ```

A verificação fica coberta em [tests/test_i18n.py](../tests/test_i18n.py):

```bash
poetry run pytest   # ou de forma restrita, poetry run pytest tests/test_i18n.py; resultados green confirmam cobertura, recusa ao inglês quando entradas faltam e preservação dos placeholders de formatação.
LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Download ready.'))"
# Esperado: Download pronto.  → prova que o novo msgid é resolvido pelo catalog compilado daquele locale.
```

## Como Internacionalizar um Arquivo de Código Já Escrito

Use esta receita para transformar um arquivo que ainda carrega literais com hardcoded (português ou inglês) no padrão orientado a catalogs descrito acima.

1. **Encontre os literais com hardcoded.** Faça grep no arquivo procurando literais visíveis ao usuário no idioma-fonte. Literais portugueses tendem a conter caracteres acentuados, o que facilita encontrá-los:

   ```bash
   grep -n "Exportando\|falha\|Erro\|Arquivo" backend/example_module.py   # esperado: números de linha e as linhas com hardcoded que devem migrar para um catalog
   grep -n 'logger\.\(info\|debug\|warning\|error\|critical\)(' backend/example_module.py   # esperado: cada chamada de log a verificar quanto a textos com hardcoded
   ```

   Anote cada literal e onde ele é emitido (linha de log, `raise`, resposta HTTP/Telegram ou corpo de e-mail).

2. **Escolha o módulo de constantes dono**, mantendo os ids próximos da sua preocupação:
   - linhas de log do servidor e e-mails → acrescente ids `LOG_*`/`EMAIL_*` em [backend/log_messages.py](../backend/log_messages.py);
   - textos de estágio/status do pipeline visíveis ao usuário → [backend/stage_messages.py](../backend/stage_messages.py);
   - erros do executor → [backend/core/execution/messages.py](../backend/core/execution/messages.py);
   - textos do bot do Telegram → [frontend/telegram/messages.py](../frontend/telegram/messages.py);
   - textos de interface do painel web → [frontend/web/messages.py](../frontend/web/messages.py);
   - erros ou mensagens locais do módulo → defina as constantes `MSG_*` no topo do próprio arquivo (o padrão de [backend/tools/validators.py](../backend/tools/validators.py)).

   Cada nova constante é o **texto canônico em inglês** (com marcadores `{placeholder}` para variáveis) mais um comentário `#:` descrevendo-a, p. ex.:

   ```python
   +#: Log message emitted once per export; {path} is the destination path substituted by the caller after lookup.
   +LOG_EXPORT_START: str = "Exporting {format} to {path}"
   ```

3. **Reescreva cada ponto de chamada** buscando o id no momento da emissão, mantendo a substituição de placeholders no lado do chamador:

   ```python
   -    logger.info(f"Exportando {fmt} para {dest}")
   +    logger.info(t(LOG_EXPORT_START).format(format=fmt, path=dest))
   ```

   e traduza para o inglês americano quaisquer docstrings/comentários em outro idioma no arquivo tocado, com parâmetros tipados conforme as regras de qualidade de código do projeto.

4. **Registre as constantes no gerador.** Acrescente o import e os ids à `MESSAGES` em [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py), e acrescente uma tradução portuguesa não vazia para cada um na tabela `TRANSLATIONS["pt_BR"]` (preserve a redação portuguesa original exatamente quando veio de strings com hardcoded, para que o texto visível ao usuário não mude).

5. **Regenere e verifique:**

   ```bash
   poetry run python scripts/gen_locale_catalogs.py   # reescreve os dois .po-fonte e compila os dois .mo
   poetry run pytest tests/test_i18n.py               # verde significa que cobertura, fallback e placeholders estão todos ok
   LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Exporting {format} to {path}').format(format='TXT', path='var/out.txt'))"
   # Esperado: a redação pt-BR da mensagem movida com as variáveis substituídas — prova de que o id se resolve pelo catalog.
   ```

## Como Adicionar um Novo Locale e Ativá-Lo

Adicionar um locale (p. ex. `es_ES`) é intencionalmente pequeno: uma tabela de traduções e configuração, sem mudanças na lógica de negócio.

1. **Ative o locale nos arquivos de configuração** (`.env` e `.env.example`, na seção de i18n do rodapé):

   ```bash
   emacs .env
   ```

   ```
   # I18N Configuration
   #LOCALE=pt_BR
   -I18N_LOCALES_ACTIVE=en_US,pt_BR
   +I18N_LOCALES_ACTIVE=en_US,pt_BR,es_ES
   ```

   `I18N_LOCALES_ACTIVE` controla quais locales são oferecidos aos usuários remotos; `LOCALE` (quando definido) seleciona o locale do servidor usado para o log e para a saída padrão.

2. **Declare o locale ao runtime.** Adicione o identificador a `SUPPORTED_LOCALES` em [backend/i18n.py](../backend/i18n.py) (linha ~20) e a `SUPPORTED_LOCALES` em [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) (linha ~409), para que negociação, a lista de locales oferecidos pelo bot e a geração dos catalogs o incluam a todos:

   ```python
   -SUPPORTED_LOCALES: tuple[str, ...] = ("en_US", "pt_BR")
   +SUPPORTED_LOCALES: tuple[str, ...] = ("en_US", "pt_BR", "es_ES")
   ```

3. **Forneça a tabela de traduções.** Em [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py), adicione um mapeamento `es_ES` à `TRANSLATIONS` com uma entrada não vazia para **todos** os ids da `MESSAGES` — o gerador valida a cobertura completa e se recusa a escrever os catalogs enquanto faltar algum id, então a primeira execução falha com clareza até que a cobertura termine. Mantenha os nomes dos placeholders na forma `{variável}` idênticos às strings em inglês:

   ```python
   "es_ES": {
       MSG_FILE_TOO_LARGE: "Archivo demasiado grande. Límite: {limit} MB.",
       MSG_DOWNLOAD_READY: "Descarga lista.",
       # ...uma entrada não vazia por id em MESSAGES...
   }
   ```

4. **Genere os arquivos de strings do novo locale.** O gerador agora escreve `backend/locales/es_ES/LC_MESSAGES/messages.po` e compila o `messages.mo` ao lado dele, exatamente como os locales existentes:

   ```bash
   poetry run python scripts/gen_locale_catalogs.py
   # Saída esperada agora lista o novo path LC_MESSAGES do es_ES além de en_US e pt_BR.
   ls backend/locales/es_ES/LC_MESSAGES/   # esperado: messages.po e messages.mo
   ```

5. **Verifique em runtime e teste:**

   ```bash
   LOCALE=es_ES poetry run python -c "from backend.i18n import t, active_locale; print(active_locale(), '|', t('Download ready.'))"
   # Esperado: es_ES | Descarga lista.  → prova que o novo catalog de locale carrega e se resolve.
   poetry run pytest                          # suíte completa ainda verde, incluindo as verificações de cobertura em tests/test_i18n.py
   ```

   Para qualquer coisa visível ao usuário no novo locale, confira a cobertura de glifos nas versões recentes de Linux, macOS e Windows (prefira símbolos amplamente suportados a emojis exóticos).

## Visualizando e Editando Traduções Existentes

- **Visualizando.** As traduções legíveis vivem nos arquivos-fonte por locale: [backend/locales/en_US/LC_MESSAGES/messages.po](../backend/locales/en_US/LC_MESSAGES/messages.po) para inglês e [backend/locales/pt_BR/LC_MESSAGES/messages.po](../backend/locales/pt_BR/LC_MESSAGES/messages.po) para o português do Brasil. Abra qualquer um deles para inspecionar msgids, textos localizados, placeholders de formatação e regras de plural.

  ```bash
  cat backend/locales/pt_BR/LC_MESSAGES/messages.po    # mostra o cabeçalho-fonte do pt-BR e os pares msgid/msgstr iniciais.
  grep -n -A1 'Processing your document' backend/locales/pt_BR/LC_MESSAGES/messages.po
  # p. ex.: msgid "Processing your document…"
  #     msgstr "Processando seu documento…"   (os números de linha mudam à medida que novas mensagens são acrescentadas.)
  ```

  O runtime carrega os arquivos binários `messages.mo` compilados, que ficam ao lado de cada `.po`; o catálogo identidade em inglês padrão mapeia todo msgid a si mesmo. Verifique, em runtime, o que um locale realmente serve:

  ```bash
  LOCALE=pt_BR poetry run python -c "from backend.i18n import t; print(t('Processing your document…'))"   # esperado: Processando seu documento…
  LOCALE=en_US  poetry run python -c "from backend.i18n import t; print(t('Processing your document…'))"   # esperado: Processing your document…
  ```

  Para uma verificação completa da pilha, inicie as interfaces sob o locale desejado e exercite a API ou o bot:

  ```bash
  cp .env.example .env 2>/dev/null || true    # apenas se você ainda não tiver um .env (ignore se já tiver).
  LOCALE=pt_BR poetry run python -m frontend.run   # então, p. ex., mande ao bot um arquivo acima do limite e espere o texto pt-BR "Arquivo muito grande.", ou chame /health para uma descrição de status localizada.
  ```

- **Editando.**
  1. Edite as entradas do locale afetado na seção `TRANSLATIONS` de [scripts/gen_locale_catalogs.py](../scripts/gen_locale_catalogs.py) (os arquivos `.po` são artefatos regenerados — não os edite à mão ou suas alterações serão sobrescritas na próxima execução).
  2. Rode o gerador novamente para reescrever o `.po` e o `messages.mo` compilado do locale:

     ```bash
     poetry run python scripts/gen_locale_catalogs.py
     ```
  3. Mantenha os nomes dos placeholders na forma `{variável}` idêntica em todos os locales, para que a substituição no chamador continue funcionando, e atente à cobertura de glifos nas versões recentes de Linux, macOS e Windows para qualquer coisa visível ao usuário (p. ex., prefira símbolos amplamente suportados a emojis exóticos quando possível).
  4. Rode `poetry run pytest` para confirmar que a suíte i18n continua passando.
