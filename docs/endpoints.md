# Endpoints & APIs

The project serves HTTP over **three separate servers**, each brought up in different ways. Confusing them is the most common source of questions, so start by separating the three:

| Server | What it is | How it starts | Host/port |
|----------|------------|---------------|-----------|
| **REST API** | The product's main JSON API (submit document, check status, download result, history). Written by us in FastAPI. | Part of `run.py` when `ENABLED_INTERFACES` includes `api`; or standalone via `backend/api/run.py`. | `0.0.0.0:8000` |
| **Web panel** | HTML interface for humans. Today it is a thin client of the REST API: renders pages and delegates upload/status/download to the API. | Part of `run.py` when `ENABLED_INTERFACES` includes `web`. | `0.0.0.0:8001` |
| **AgentOS** | Inspection showcase for the AI agents. Its routes are automatically generated by Agno — we write none of them ourselves. | Separate runtime: `python -m frontend.agent_os`. Does not run the pipeline. | `localhost:7777` |

`ENABLED_INTERFACES` (default `api,telegram,web`) controls which pieces come up together in `run.py`. Telegram and the Web panel are **clients** of the REST API (via `frontend/clients/api_client.py`); the API is the source of truth.

---

## Part 1 — REST API (`backend/api`, JSON)

Defined in [backend/api/app.py](../backend/api/app.py), with routes in [backend/api/routes/](../backend/api/routes/). This is the real JSON API: it receives `multipart/form-data` on upload and returns **JSON** everywhere. All routes sit under prefix **`/api/v1`** and have per-IP request limits. Processing is **asynchronous**: upload enqueues a job and replies immediately with a `task_id`; you track progress by polling.

### Jobs (submit & track)

| Method | Route | What it does | Response | Limit |
|--------|-------|--------------|----------|-------|
| POST | `/api/v1/jobs` | Submits a document for processing. Form fields: `document_file`, `mode` (`detalhado`, `medio`, `normal`, `baixo` or `ocr`; default `normal`), `custom_prompt` (up to 6000 chars), `thinking_mode`, `email`, `source`. Validates extension/size and enqueues. | `202` with `task_id` and message. `400` if file or prompt invalid. | 5/min |
| GET | `/api/v1/jobs/{task_id}` | Checks the state of a job. | JSON `JobStatus`: `task_id`, `arquivo`, `status`, `progresso` (0–1), `etapa_atual`, `erros[]`, `download_url` (when ready), `criado_em`, `fim`. | 60/min |
| POST | `/api/v1/jobs/{task_id}/cancel` | Cancels a running job. | JSON `{task_id, status}`. | 10/min |

### Download (finished result)

| Method | Route | What it does | Response | Limit |
|--------|-------|--------------|----------|-------|
| GET | `/api/v1/download/{token}` | Metadata for a completed task's result. The `token` comes from the job's `download_url`. | JSON `DownloadInfo`: `filename`, `stem`, `criado_em`, `formats[]` (each with `ext`, `label`, `size`, `url`). `404` if token is invalid/expired. | 10/min |
| GET | `/api/v1/download/{token}/{format}` | Actually downloads one format: `txt`, `docx`, `pdf`, `pdf_ua`, `html`, `mp3` or `zip` (the all-in-one bundle). | The file itself. `400` bad format, `404` token/file missing. | 20/min |

### History & health

| Method | Route | What it does | Response | Limit |
|--------|-------|--------------|----------|-------|
| GET | `/api/v1/history?limit=20` | Lists the most recent conversions (limit 1–100). | JSON `HistoryItem[]`: `task_id`, `arquivo`, `extensao`, `status`, `modo`, `pipeline`, `erro`, `resultado_resumo`, `tempo_segundos`, dates. | 30/min |
| GET | `/api/v1/stats` | Aggregated stats. | JSON `{total, sucesso, erros, tempo_medio_segundos}`. | 30/min |
| GET | `/api/v1/health` | Health and model-connectivity check. | JSON `{status, model_client, model_name, model_reachable, queue_size}`. | 30/min |

Observations:

- **Errors are always JSON** (`{"detail": "..."}`): `400` validation, `404` not found, `429` rate limit, `500` internal error. There is a global per-IP limit in addition to the per-route ones.
- The `pipeline` field in history records which engine ran the job — `legacy` or `pddl` (see `PIPELINE_ENGINE` in [architecture.md](architecture.md)).
- Standard interactive FastAPI docs at `GET /docs` and `GET /openapi.json`.

## Part 2 — Web panel (`frontend/web`, HTML)

Defined in [frontend/web/app.py](../frontend/web/app.py). It is a **server-rendered** app (Jinja2 templates) that serves HTML pages and, underneath, calls the REST API. It has no processing logic of its own: the upload/download routes just forward to `/api/v1`.

| Method | Route | What it does | Response |
|--------|-------|--------------|----------|
| GET | `/` | Home page with the submission form. | HTML. |
| GET | `/advanced` | Advanced page (custom prompt + "thinking" mode). | HTML. |
| POST | `/process` | Takes the form and forwards the upload to `POST /api/v1/jobs`. | HTML with the confirmation/error. |
| POST | `/advanced/process` | Same, plus `custom_prompt` and `thinking_mode`. | HTML. |
| GET | `/download/{token}` | Download page; queries the API and builds links to `/api/v1/download/...`. | HTML listing the formats. `404` if the token expired. |
| — | `/static/*` | Static files (CSS, JS, images). | The file itself. |

I.e., the Web panel is the **face** for humans; the REST API is the **engine**. A terminal app, Telegram or an external script all talk to the API directly, without going through the panel.

## Part 3 — AgentOS (generated by Agno)

When `AgentOS(...)` is instantiated in [frontend/agent_os.py](../frontend/agent_os.py), Agno **builds a hundred JSON REST routes on its own** — the Agno panel (os.agno.com) and agent-ui consume those routes. We write none of them; they come for free. The exact list varies with the Agno version and what is registered, so the source of truth is that runtime's `openapi.json` (see "How to check it yourself" at the end). It is a **development/inspection** tool: use it to chat with each agent individually and to see sessions, memory, metrics and traces. It does **not run** the accessibility pipeline.

The key point: many of these routes exist always, but they only return something useful once their corresponding resource is configured. In our setup we register **two agents** (`VisionAgent` and `DataAgent`), one SQLite session store (`agentos.db`), and no teams, workflows or knowledge base. Hence four groups:

- **Meaningful in our setup** — `/agents/*` (talk to Vision/Data and see executions), `/sessions`, `/memories`, `/metrics` (the graphs), `/traces`, plus `/health`, `/config`, `/info`, `/models`.
- **Present but empty** — `/teams`, `/workflows`, `/knowledge`, `/learnings`, `/eval-runs` (we don't register those resources). The pipeline today runs **outside** AgentOS, so `/workflows` shows nothing.
- **Present but disabled** — `/approvals`, `/components`, `/schedules`, `/service-accounts` (Agno itself marks them "Disabled").
- **Utilities** — `GET /docs` (Swagger), `GET /redoc`, `GET /openapi.json`.

### How to check it yourself

AgentOS routes come from what you register; to see the current truth, bring up the runtime and query its spec:

```bash
python -m frontend.agent_os            # comes up at localhost:7777
curl http://localhost:7777/openapi.json   # all routes, generated on the fly
```

If one day we register a Team, a Workflow or a knowledge base in `agent_os.py`, the routes that are now empty will start answering — without writing a single endpoint.
